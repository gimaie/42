# get_next_line
📖 get_next_line - ファイルディスクリプタからの行読み込み
指定されたファイルディスクリプタから、呼び出すたびに次の1行を読み取る関数を実装するプロジェクトです。

本プロジェクトの核心は、static 変数を用いたデータ保持と、BUFFER_SIZE の変動に左右されない堅牢なメモリ管理にあります。1行の区切り（\n）を見つけるまで効率的に読み込み、残ったデータを次回の呼び出しのために正確に残しておくロジックを構築しました。

🎯 技術的な達成目標
データの永続化: static 変数を使用し、関数終了後も読みかけのデータを保持する仕組みの実装。

動的メモリ管理: read で取得したデータを既存のバッファに結合（ft_strjoin）し、必要に応じて伸縮させる処理。

境界条件の処理: ファイルの終端（EOF）、空ファイル、および改行を含まない最終行の正確なハンドリング。

マルチファイルディスクリプタ（Bonus）: 配列を用いた static 変数の管理により、複数のファイルを並行して読み取る機能の実装。

🛠️ 技術スタック
言語: C言語 (C99)

主要な仕組み: static 変数、ファイルディスクリプタ (fd)、システムコール (read)。

ビルド: -D BUFFER_SIZE=n フラグによる、コンパイル時のバッファサイズ指定。

💡 実装の詳細と学習成果
1. static 変数による読み込みバッファの保持
get_next_line 関数内で定義した static char *rem（または rem[OPEN_MAX]）により、前回の呼び出しで読み込みすぎたデータを保持しています。

実装: 関数呼び出し時に、まず rem 内に改行が含まれているかを確認します。含まれていない場合のみ read を実行し、改行が見つかるまでデータを蓄積（継ぎ足し）していきます。

成果: 関数の寿命を超えてデータを管理するスコープの概念を深く理解しました。

2. 厳密なメモリ解放とポインタの更新
データの結合や切り出しの際、メモリリークを防止するために free のタイミングを徹底しました。

実装: read_manage_rem 内で ft_strjoin を行う際、結合前の古いポインタを即座に free して tmp に置き換える処理をループ内で繰り返しています。

成果: 文字列を更新する際の「確保 → 結合 → 解放 → 代入」という一連のサイクルを確実に実装する能力が身につきました。

3. 改行位置に基づくバッファの分割処理
改行コード（\n）を検知した際、その前後でバッファを正確に分割する check_rem 関数を実装しました。

実装: ft_strndup で改行までを返り値用の行として切り出し、ft_strdup で改行以降のデータを新しい rem として保存しています。

成果: メモリアドレスのオフセット計算（nl - *orem + 1）を用いた、ポインタ演算による文字列操作の理解が深まりました。

📝 実装上のエピソード：ダブルポインタによる状態更新の制御
本プロジェクトで最も技術的な工夫を要したのは、static 変数のポインタを、サブ関数から直接書き換える設計です。

read_manage_rem や check_rem といった関数に、static char *rem のアドレスを char **rem（ダブルポインタ） として渡しています。
これにより、サブ関数内で free と再割り当てを行った結果を、get_next_line 本体の static 変数に即座に反映させることが可能になりました。

単なる値渡しではなく、ポインタのポインタを扱うことで、「どこでメモリが解放され、どこの住所が更新されているのか」というメモリマップを常に意識する必要があり、複雑なデータ構造を扱う際のデバッグ能力が飛躍的に向上しました。

🏃‍♂️ 使用方法
本リポジトリのコードは、課題の要件に従い main 関数をコメントアウトしています。

Bash
# BUFFER_SIZEを指定してコンパイル
cc -Wall -Wextra -Werror -D BUFFER_SIZE=32 get_next_line.c get_next_line_utils.c main.c

# 実行（標準入力やファイルから読み込み）
./a.out
